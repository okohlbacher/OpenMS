• Findings from static review of the supplied benchmark-only packet. Two concrete defects found; both are introduced in this packet (new harness/gate code), not pre-existing.

  ---

  **FINDING 1 — HIGH — `final-gates.py` iterparse pruning destroys spectrum content before it is audited; the claimed independent RT-window / precursor-IM evidence cannot be produced by this code**

  - **Source:** `results/gap-bench/reproduce/final-gates.py`, the `ET.iterparse(..., events=('start','end'))` loop and the subsequent `assert times and min(times)>=600 and max(times)<=1200,(min(times),max(times))`.
  - **Defect:** On every `end` event the code unconditionally executes `e.clear(); if len(stack)>1: stack[-2].remove(e); stack.pop()`. `remove(e)` detaches each element from its parent **at its own end event**, i.e., before the enclosing `spectrum` end event fires. `cvParam` elements are detached from `scan` when the `cvParam` ends; `scan` elements are detached from `scanList` when the `scan` ends; `scanList`/`precursorList` are detached from `spectrum` when they end. Consequently, when `e.tag==N+'spectrum'` is handled, `e.findall('.//'+N+'scan')` and `e.findall('.//'+N+'precursor')` always return empty. `times` stays `[]` and `precursor_im` stays `0`.
  - **Trigger:** Running `final-gates.py` at all. The `assert` short-circuits on empty `times` and the message expression `(min(times), max(times))` then raises `ValueError: min() arg is an empty sequence` — the script crashes at that line, never writes `im-window-metadata.json`, never runs the final inflater verification, and never touches `FINAL_GATES_COMPLETE`.
  - **Impact:** (a) The claimed independent XML audit ("RT bounds 600.016..1199.997 s, 22032 finite precursor IM CV terms") cannot be the output of this script as supplied — that claim is unsupported by the code. (b) Pipeline-blocking: `FINAL_GATES_COMPLETE` is never created and `final-decompressor-correctness.json` is never written; `identity()` in `run-gap.py` reads `final-decompressor-correctness.json`, so `bind_identity()` in `run-gap.py run` would raise `FileNotFoundError` and the timed matrix cannot start in the documented order.
  - **Minimal fix:** Only prune after processing spectra — e.g., handle `end` events as: if `e.tag==N+'spectrum'`: extract scan/precursor data, then `e.clear()` and `stack[-2].remove(e)`; for non-spectrum elements, just `stack.pop()` (optionally `root.clear()` periodically). Do not `remove()` descendants while inside a spectrum.
  - **Minimal test:** Run the fixed gate on the real `pasef-im-600-1200s.mzML` and assert `metadata['spectra_with_rt']>20000`, `600<=min_rt<=max_rt<=1200`, `finite_precursor_im_cv_terms==22032`; also run it against the `test-audit.py`-generated `im.mzML` (2 spectra, known RTs `0.0/0.5`, 2 precursor-less spectra) and assert exact recovered values.

  **FINDING 2 — MEDIUM — `test-audit.py` RSS-floor control rests on a false kernel premise: `fork`+`exec` does not inherit the parent's `hiwater_rss`, so the strict floor-ordering assertions fail deterministically**

  - **Source:** `results/gap-bench/reproduce/test-audit.py` (the `parent=bytearray(128*1024*1024)` block with `assert small['native_peak_rss_bytes']<small['wait4_max_rss_bytes']` and `assert 0<small['native_wait4_peak_rss_bytes']<small['wait4_max_rss_bytes']`); matching rationale in `run-gap.py` module docstring ("wait4 retains its inherited parent floor") and `native-meter.cpp` header comment.
  - **Defect:** On Linux, a forked child inherits `mm->hiwater_rss` (dup_mm memcpy), but `execve` installs a fresh zeroed `mm_struct`, resetting `hiwater_rss` to 0. Every process in this harness's launch chain is exec'd: Python → fork/exec `taskset` → exec `native-meter` → fork/exec `launcher` → exec benchmark. Therefore no measurement in the chain carries the Python parent's peak RSS. Python's `wait4` on the `taskset`/`native-meter` PID returns `max(native-meter, reaped tool)` = the tool's own peak; `native-meter`'s `wait4` returns the same tool peak; the in-process VmHWM is the same kernel hiwater. The three values are equal (modulo one page of teardown), so `native_wait4_peak_rss_bytes < wait4_max_rss_bytes` is a strict `<` between equal quantities and fails deterministically; `native_peak_rss_bytes < wait4_max_rss_bytes` is at best flaky-equal.
  - **Trigger:** `python3 test-audit.py` reaches the floor block; raising the Python parent's RSS by 128 MB changes nothing post-exec.
  - **Impact:** The shipped negative/positive control suite fails as written, contradicting the "tests pass" status. It also invalidates the framing claims "wait4 retains its inherited parent floor" and "raw Python floor separately retained" — there is no Python floor in either number, so `raw_driver_wait4_rss_mib` in `analyze.py` is simply a duplicate of the native wait4 value, not evidence of an excluded floor. The benchmark RSS numbers themselves are unaffected (they are valid with or without the supervisor, which still provides the native wall/rusage counters).
  - **Minimal fix:** Replace the strict floor-ordering assertions with equality/cross-check assertions, e.g. `assert abs(small['wait4_max_rss_bytes']-small['native_wait4_peak_rss_bytes'])<8*1024*1024` and keep the existing `<8 MiB` VmHWM-vs-wait4 check; if an inherited-floor demonstration is desired, add a fork-without-exec control child (that is the only case where Linux propagates `hiwater_rss`). Correct the two docstrings/comments to say exec already resets the parent high-water mark.
  - **Minimal test:** `python3 -c "import subprocess,resource; b=bytearray(128*1024*1024); b[::4096]=b'\\1'*32768; subprocess.run(['/usr/bin/true']); print(resource.getrusage(resource.RUSAGE_CHILDREN).ru_maxrss)"` prints ~1–2 MB, not ≥128 MB — demonstrating no post-exec floor; then assert the harness's three RSS values agree within one page.
